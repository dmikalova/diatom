# 7. One window per repo, with its scheduler inside

This decision records how diatom's process and window are laid out, and how its configuration is found.

## Context

Several goals may run in a repo at once, while others are parked for days.

diatom first ran one scheduler per machine across every repo it knew about, with a repo picker, a machine-wide focus and a machine-wide session cap. Working in two repos at once rarely needs them to share a queue, and one diatom per repo is simpler to run and to reason about: everything it touches is in the repo it was started in.

It then ran a headless scheduler per repo beside a zellij session of four panes: review, status, questions and intake. The panes showed everything at once, each its whole slice, rather than the right thing at the right time. Answering questions was hardest: the questions pane had no room to say what a goal was for, and the context changed with every answer. zellij bought two things. Detaching kept the agents running with nobody watching, which isn't wanted. Text could be selected inside one pane.

A single Bubble Tea program can hold several parts that each take the keyboard, like a web page's navigation beside its content, and handle the mouse itself.

A directory of repos that are worked on together, such as one organization's, is a different thing from a machine's every repo. The repos share a config, their goals are few, and the human watches them all at once. One window per repo makes that many windows, each with its own session limit, which together overload the machine.

## Decision

**diatom works in one workspace: the repo it is started in, or, when it is started outside a repo, every git repo directly under that directory. `diatom` opens one window on the workspace, and the window runs one scheduler for every repo in it. Closing the window suspends the sessions (ADR 0012), so nothing runs while diatom is closed.**

- **Every command finds its workspace from the directory it runs in**, anywhere in a repo, a goal's worktree included. Started inside a repo, the workspace is that repo. Started outside one, the workspace is every directory one level down that holds a `.git`. A repo joins as it is: diatom keeps nothing in it and makes the state it needs outside it ([ADR 0013](0013-diatom-keeps-its-state-outside-the-repository.md)). Outside a git repo and over a directory with no repo under it, diatom refuses to run. A repo diatom cannot name, because it has no origin, is left out and said so. Every command but the window works in one repo, so it is run in the repo it is about.
- **The scheduler picks the highest-priority ready task across every active goal of every repo.** Each repo sets its own maximum number of sessions, and the top of the config sets how many run across all of them at once. Every repo of the workspace keeps one of those sessions to itself, so a busy repo never starves a quiet one. The scheduler takes each repo's lock, `run.lock` in that repo's state directory. A window whose repos are locked by another window runs no scheduler and only views, though answering and reviewing still work there, since everything the window changes is a file in the state directory. The scheduler logs to the first repo's `diatom.log`.
- **Whether a goal is active or parked is saved in the goal itself**, so it survives restarts. New goals start in planning.
- **The window is a nav down the left and a main pane showing what the nav selects.**
  - The nav lists Next, the intake, and the goals being worked on, each on two lines: a glyph for where it stands and its title, then the one thing about it that matters most now, what waits on the human first. Over a workspace of several repos, each goal's title is prefixed with its repo, and each repo has its own intake line. The glyph is a robot while an agent works on the goal, and the merge sign while diatom commits a session's work or lands it. Next's second line counts what waits, then the agents running and the git work under way. A menu at its foot holds the spending, day by day and each day by goal and session, the finished goals, the latest first, and the scheduler's log. Its footer shows what the work has cost today, over the last 7 days and over the last 30, red where that spends the budget (ADR 0004), which opens the spending, and the scheduler's health, which opens the scheduler's log. The intake box sits at its foot.
  - **Over a workspace each repo is a heading in the nav, and its goals sit under it.** The nav is narrow and a goal's title is the part worth reading, so the repo is named once, above that repo's lines, not on every one. The heading opens the repo's config page, which sets its levers ([ADR 0013](0013-diatom-keeps-its-state-outside-the-repository.md)). The repo's own intake is the first line under its heading. Everything the main pane shows names the repo too: the goal's page in its breadcrumb, and each item of Next above the goal it is about. The human must always know which repo they are answering about.
  - **The spending and the health are the workspace's, not the first repo's.** One scheduler spends one budget, so the spending adds up every repo's sessions, and names each day's goals with the repo they are in. The health names the first repo that is held up. The log is still the first repo's.
  - **Next** is everything waiting on the human, one item at a time: goals ready to finish, then plans to sign off, then questions, then hunks to review, each level in the nav's order of goals. A goal ready to finish comes first because its work is done and the goals waiting for it start once it lands; a plan holds a whole goal up and a question a task, and a review holds up nothing. A goal whose pull requests are already open is not in Next at all and sinks to the foot of the nav's goals: the human has them, diatom can do nothing more for it, and it must not come between them and the goals that still move. A goal ready to finish can instead be given more work, as a task of its own, or put off behind the rest. The hunks finishing a goal brought, catching up with its base, hold up its landing, so they come with the goals ready to finish. Answering moves on to the first item left, and nothing else changes the item shown.
  - An item of Next has three parts: what its goal is for, which opens the goal's page; the item itself; and the answer, or what can be done.
  - A goal's page says where it stands and what it is for, then offers its actions and its review, its plan, and its tasks, each opening to its sessions and their steps.
  - Tab moves through the nav, the main pane's parts and the intake box. Clicking selects and focuses, the wheel scrolls, and dragging the nav's edge resizes it.
  - An intake carries what the main pane showed when it was sent, as a clue for triage (ADR 0009). Over a workspace it goes to the repo the nav has selected, which the box's label names.
  - With the terminal in the background, a notification says when Next has something again after having nothing.
  - **A problem comes before everything else in Next**, because diatom itself is stopped and the goal it is on runs no more ([ADR 0014](0014-problems-are-what-diatom-cannot-get-past.md)).
- **There is one config file, and a repo's settings are a block in it** ([ADR 0013](0013-diatom-keeps-its-state-outside-the-repository.md)). The walk-up through the parent directories is gone, and so is the config in the repo.

The cost is that the window holds the mouse: the terminal's own selection needs its modifier key and runs across the whole window. So the window selects for itself: dragging in the main pane selects text within the pane alone and copies it on release, and `y` or cmd+c copy the selection, or else the part that has the keyboard.

# 3. Goals integrate continuously and never rebase mid-run

This decision records how a goal's work moves through branches and worktrees.

## Context

A goal such as "implement the new set" splits into workstreams with dependencies between them: engine, then cards, then web. Each workstream needs its own worktree so they don't interfere. Downstream workstreams need upstream work soon after it lands. The card workstream may also need engine changes of its own. Review is asynchronous (ADR 0001), so waiting for approval before sharing work would bring back the blocking diatom exists to remove. Review decisions are tied to commit SHAs, and rewriting history would break that link.

## Decision

**Each goal has an integration branch. Each workstream has a workstream branch off it, in its own worktree.**

- **The branches are `diatom/<goal>/integration` and `diatom/<goal>/ws/<workstream>`.** The integration branch can't simply be `diatom/<goal>`, because git can't hold a branch and branches under the same name.

- **Every commit that passes the gate is merged into the integration branch immediately**, without waiting for review.
- **A workstream merges the integration branch in before each task**, so downstream work always sees current upstream work.
- **Workstreams are scoped by purpose, not by path.** The card workstream may edit engine files. When two workstreams edit the same code, the harness creates a conflict-resolution task instead of blocking either one.
- **Nothing is rebased while a goal is running**, because commit SHAs anchor review decisions.
- **Revisions land as fixup commits**, one per original commit revised (`fixup! <original subject>`, or `fixup! <SHA>` when another commit of the goal has the same subject and autosquash could pick the wrong one). The agent marks each revision done as soon as it finishes it, and the harness splits the session's work into fixups at those points. The gate runs once, on the session's final files: a fixup's own tree is never merged anywhere, and autosquash moves it beside its original anyway. Commits are sized to keep the gate passing, not to one change each.
- **A goal's base is the remote's default branch**, the one `origin`'s HEAD points at, usually `main`. It is not the branch the human has checked out: a window is often opened on a feature branch, and a goal based on that one lands nowhere. The base is fetched before a goal's integration branch is created, so the goal starts from the remote's tip rather than from whatever was last pulled, and a base with no local branch at all starts from the remote-tracking branch. A repo with no remote falls back to the checked-out branch.
- **A goal follows its base branch as it moves.** On each pass, the scheduler merges what the base branch gained into the integration branch of every goal at work, parked or done, so no session starts on a base that has moved on. What diatom pushes moves the remote-tracking branch at once, and the scheduler fetches the base branches every two minutes for what lands by other hands. Only the integration branch moves: each workstream takes it in before its next batch, as always, so a running session finishes first, and no agent merges or pulls the base itself. A goal still planning takes its base in once it starts, a waiting one as it stops waiting, and one pushed or opened upstream is left alone. A conflict goes to an agent as a conflict task, as it does when landing, and a done goal is active again until it is resolved.
- **A goal catches up with its base branch before it lands, too.** Landing fetches the base branch and merges what it gained into the integration branch. When that conflicts, landing stops: a conflict task merges the base into the goal's last workstream for an agent to resolve, the goal is active again, and the resolution is reviewed like any commit before the goal can land. A goal is never rebased onto its base; the base is merged in.
- **An active goal's integration branch is mirrored to the remote.** After each integration, the tip is force-pushed with a lease to `diatom/<goal>/review`, the branch the goal's pull request lives on from its first commit (ADR 0014). The mirror only adds a push; nothing is rebased and no history is rewritten, so the rule below still holds.
- **A done goal is prepared for landing, then merged into its base or opened as a stack of pull requests.** Finishing a goal replays its commits onto the base branch's tip without the merges, squashing each fixup into the commit it revises as `git rebase --autosquash` would. The commits are grouped by workstream in dependency order, the goal's ADRs with the first, and each group is one pull request of a stack on `diatom/<goal>/pr/<workstream>`. Grouping reorders commits, so when a workstream built on another's later change to the same code, the goal becomes one pull request in the order the work was done instead. When the base changed the goal's own code, the commits no longer apply on its tip as they are: they are then replayed onto it in the order they were made, and landing stays mechanical. A conflict is resolved by an agent once, in the catch-up, and reviewed there; settling it again commit by commit would be a second agent run and a second review of the same conflict. Diatom runs its merges and picks with rerere on, whatever the repo's own setting: committing the catch-up records how its conflicts were resolved, and a pick meeting the same conflict is settled the same way, with no conflict marker left. The first commit git still can't replay is squashed, with every commit after it, into one commit of the reviewed merge's files, keeping each one's message. Taking either side, or the reviewed merge, file by file would lose a change from one side or bring in a later commit's, so the squash covers the rest of the goal rather than one commit. A merge into a workstream whose every conflict rerere settles counts as clean, and goes to the gate rather than an agent. A layout an older diatom made, with an agent's settlements, is laid out again. Merging into the base pushes to the remote's base branch, then fast-forwards the local one where that can't lose anything: never over the human's own commits or uncommitted changes to what landed, and never with a stash. When the rebased files differ from the reviewed merge, a last commit brings them to it. A merge commit would keep the commits as they were, but repos that require linear history refuse it. A saved layout with a merge or an unsigned commit is laid out again rather than landed. Commits diatom makes without a worktree are signed when `commit.gpgSign` is set, as `git commit` signs the rest. A merge that a conflict or gate-repair task fixed holds changes no commit has, so a last commit carries them: the layout always ends with the files the integration branch passed the gate with, merged with whatever the base branch gained since. The gate runs on each pull request's tip, because one may pass only with those after it. A goal whose last commit fails the gate never lands, and is never forced: a gate-repair task on its last workstream, with the gate's output, goes to an agent, and the goal is active again until the task is done. Landing it then pushes the branches and opens the stack with `gh`, or pushes straight to the base branch, never forcing: `P`, `F` and `d` on the goal's page, or in Next. The integration branch and its review records are left as they were.
- **A done goal stays in view until it is finished: merged upstream, with the checks passing there.** Done means the agents' work is over; the goal isn't off the human's plate until it has landed. The scheduler checks each done goal every two minutes. It fetches the base branch from the remote, and the goal counts as merged once that branch holds all of the goal's changes, however they got there: merged, squashed, rebased or pushed. The checks are then read from the branch's tip upstream with `gh`. A failing check keeps the goal done and shows red on its page. A repo with no checks finishes ten minutes after the merge, once none have shown up. A finished goal's worktrees are removed, and its branches are kept.
- **A goal can wait for others.** Nothing of it runs, grilling included, until each goal it waits for is finished: merged upstream with its checks passing, since done alone leaves its work off the base branch. Its integration branch is created then, from the newer of the base branch and the upstream branch it follows, so a goal that landed by pull request is in it before the human pulls. A branch made before, as the grilling that found the goal must wait makes one, has the base merged into it once for each goal it waited for, as it stops waiting; a merge that conflicts goes to an agent, as catching up before landing does. Goals that edit the same code wait for each other rather than overlap, since two goals running side by side would otherwise only meet when the first lands, and then in a conflict for the second. A goal can't wait for itself or in a loop.
- **Goals are isolated.** Two goals, even in the same repo, never share a branch or a worktree. A goal is planning, active, parked, done or finished. Parking stops new tasks and leaves everything else in place, so resuming loses nothing.
